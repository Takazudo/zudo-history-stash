Zudo History Stash is a small, Git-shaped store for versioned UTF-8 text and exact binary bytes on
Cloudflare Workers. It gives each path an append-only history, explicit compare-and-set writes,
stored and candidate diffs, rollback as a new version, consumer-owned approval through proposals,
and advisory live-refresh signals. It is not Git hosting and it is not a general filesystem.

Your application calls the Stash Worker. D1 is authoritative for stash metadata, file heads, history,
and inline bytes; larger immutable bytes live in a private, content-addressed R2 bucket. Representation
(`text` or `binary`), content access (`inline`, `raw`, or `deleted`), transfer (`json`, `single`, or
`multipart`), storage (`d1` or `r2`), and diff eligibility are independent. A valid UTF-8 body remains
`text` above 5,000,000 bytes; size never infers representation. The separately deployed Viewer reaches
the Stash Worker through an authenticated service binding. R2 is never a public object API.

## When it fits

History Stash works well when a service needs per-path history or an audit trail, a caller must fence
concurrent writes, reviewers need an immutable candidate diff, or an interface should refresh after
advisory change events.

Choose a different system when you need atomic commits across multiple files, branches and merges,
or built-in reviewer roles and review comments. History Stash supports binary and byte-range delivery,
but the Viewer previews only bounded text and allowlisted raster images and unsupported browsers
refuse raw downloads above 32 MiB instead of buffering them. Approval policy and user identity remain
responsibilities of the consuming application.
