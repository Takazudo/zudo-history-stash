Viewer Worker は、ビルド済みのシングルページアプリケーションを配信し、Stash API の名前空間だけを
プロキシします。Viewer を信頼済みのオペレーター画面として保護しつつ、Stash API 独自の Bearer トークンと
スコープの強制も維持してください。

## アセットをビルドしてルーティングを設定する

`workers/viewer/wrangler.toml` をデプロイする前に、ライブラリと Viewer のアセットをビルドします。その
`ASSETS` バインディングは、この設定からの相対パス `./dist` を指します。クライアントルートがアプリへ
到達するように `not_found_handling = "single-page-application"` を維持し、アセットへのフォールバックより
先に API トラフィックが Worker へ到達するように `run_worker_first = ["/api", "/api/*"]` も維持してください。

アップストリームの選択順序は厳密に次のとおりです。

1. 空でない、前後の空白を除いた `STASH_BASE_URL` を最初に使います。
2. それがなければ `STASH` service binding を使います。
3. どちらも利用できない場合、誤解を招くプロキシレスポンスを返さず、Worker は失敗します。

したがって、`STASH_BASE_URL` は設定済み service binding より優先度の低いフォールバックではありません。
HTTP の Stash オリジンを意図的に対象とするデプロイではこれを使い、`STASH` は service-bound な
デプロイで使ってください。

## プロキシの範囲を狭く保つ

Worker は `/api/v1/*` をプロキシし、それ以外の `/api` パスを拒否します。リクエストのメソッド、
クエリ文字列、本文を保持し、次の小文字表記のヘッダーだけを転送します。

- `authorization`
- `content-type`
- `if-none-match`
- `idempotency-key`
- `x-stash-client-id`

Cookie と任意のブラウザーヘッダーは転送されません。Viewer は `STASH_ADMIN_TOKEN` を保存せず、
検証済みの Bearer トークンはブラウザーが提供します。Cloudflare Access または別の外側の境界は、
`/v1/me` のスコープ検査に代わるものではありません。

Server-Sent Events がレスポンスバッファリングなしで最初のチャンクをストリームできるように、レスポンスを
変更しないまま返します。下流での中断と本文のキャンセルは、選択した `fetch` または service-binding の
アップストリームへ伝播します。ミドルウェア、可観測性、エラー処理を追加するときも、この動作を
維持してください。

## オリジンを整合させて安全に検証する

ブラウザーの通信経路を一つ意図的に選んでください。通常の Viewer フローは同一オリジンの `/api` プロキシを
呼び出します。ブラウザーから Stash オリジンも直接呼び出す場合は、意図した Viewer またはホストの
オリジンだけを Stash の `ALLOWED_ORIGINS` に含めます。CORS を認証として使わないでください。選択した
トポロジーに合わせて、Viewer のオリジン、Stash のルート、CORS ポリシーを整合させます。

次の順序でデプロイします。

1. 新しい Viewer アセットをビルドします。
2. 選択した設定のアセット、ルート、サービスまたはベース URL、環境バインディングを検証します。
3. 選択した Wrangler 設定でデプロイします。
4. ブラウザーナビゲーションとして `/login` を取得し、ビルド済みの HTML シェルが返ることを確認します。
5. Viewer 経由で `/api/v1/health` を取得し、Stash のヘルス契約を満たすことを確認します。
6. それ以降の読み取り専用のプリンシパル検査と既知の正常な読み取りには、最小権限のテスト認証情報を使います。

Bearer トークンを URL に貼り付けたり、手軽な変更操作を実行したりしてデプロイをテストしてはなりません。
[トラブルシューティング](./troubleshooting.mdx)を使い、アセット、アップストリーム選択、オリジン、認証の
障害を切り分けてください。
