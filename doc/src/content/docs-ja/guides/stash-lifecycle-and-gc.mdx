stash の削除は論理削除です。設定された復元期間中はデータが保持されますが、通常のルートでは
存在が秘匿され、有効な stash トークンはすべて失効します。名前が解放されたり再利用されたりする
ことはありません。期間内に復元すると、保存済みのファイルと履歴は維持されますが、認証情報は
復活しません。復元後に新しいトークンを発行してください。

コミット済みのデプロイ設定では、現在 `STASH_DELETE_GRACE_DAYS` が 30 に設定されています。
レスポンスの `restoreUntil` を正しい期限として扱ってください。この設定は変更可能であり、永続的な
プラットフォーム定数ではありません。不明な stash、live の stash、復元期限と同時か期限後の
削除済み stash は、復元操作から意図的に区別できません。

## GC の実行

GC は管理者専用でページ分割され、種別ごとにフェンスされた lease で保護されます。`r2-orphans` は古くて
参照されていない非公開オブジェクトを削除し、`ledger` は期限切れの冪等性行を削除します。`content` は、
content grace より古く、version、live change set の entry、進行中の upload session のいずれからも参照
されていない `blobs` / `byte_blobs` 内の D1 content row を削除します。`change-sets` は retention window
経過後の expired または rejected change-set row を回収します。種別ごとに関数を別々に実行してください。
この関数は dry-run の全ページを完了し、呼び出し側が各ページのカウンターを確認できるようにしてから、
live の削除を開始します。

{/* zhs-example: consumer-gc */}

```ts
import {
  createStashClient,
  type GcKind,
  type GcRunResult,
  type StashClient,
} from "@takazudo/zudo-history-stash";

async function runPass(input: {
  client: StashClient;
  kind: GcKind;
  dryRun: boolean;
  maxObjects: number;
  inspect: (page: GcRunResult) => void;
}) {
  let cursor: string | undefined;
  do {
    const result = await input.client.admin.gc.run({
      kind: input.kind,
      dryRun: input.dryRun,
      maxObjects: input.maxObjects,
      ...(cursor === undefined ? {} : { cursor }),
    });
    if (!result.ok && result.error.code === "gc-busy") {
      return { kind: "busy" as const };
    }
    if (!result.ok) {
      return { kind: "failed" as const, failure: result };
    }

    input.inspect(result.value);
    if (result.value.error !== null) {
      return { kind: "failed-page" as const, error: result.value.error };
    }
    cursor = result.value.cursor ?? undefined;
  } while (cursor !== undefined);

  return { kind: "complete" as const };
}

export async function collectGarbageSafely(input: {
  baseUrl: string;
  adminToken: string;
  kind: GcKind;
  maxObjects: number;
  inspect: (page: GcRunResult) => void;
}) {
  const client = createStashClient({ baseUrl: input.baseUrl, token: input.adminToken });
  const dryRun = await runPass({ ...input, client, dryRun: true });
  if (dryRun.kind !== "complete") {
    return { phase: "dry-run" as const, outcome: dryRun };
  }

  const live = await runPass({ ...input, client, dryRun: false });
  return { phase: "live" as const, outcome: live };
}
```

scheduled handler は 80 objects を要求し、確定した順序 `content`、`change-sets`、`ledger`、`r2-orphans` で
実行します。content と change-sets は flat な 六 operation の page cost なので最初に実行します。ledger は
multipart cleanup が cleanup row ごとに 二 operation を追加し、admission floor は 六 でも cost が unbounded
になるため 三 番目です。まだ処理していない種別への downstream admission を予約し、その値を ledger cleanup
limit に渡します。R2 は `budget.remaining - 5` により自ら縮退でき、他の種別を枯渇させないため最後です。
統合済み scheduled test の 19-row fixture では、最初の R2 page は 一 object でした。content と change-sets
は `6 + 6` operation を使い、ledger は cleanup row を 9 件（`4` setup + `3` tail + `9 × 2` per row =
`25`）受け入れ、R2 固定 7 operation の残りは `45 - 12 - 25 - 7 = 1` です。content page は D1 row だけを
削除して R2 には触れないため、object は後続の `r2-orphans` page まで課金対象です。`content` を dry、次に
live の順で実行してから、`r2-orphans` を実行してください。

期限切れまたは rejected の change set は、期限切れまたは却下の後 30 日間、
`GET /v1/stashes/{name}/change-sets?status=expired|rejected` で一覧取得できます。その後 `change-sets` job
が `change_sets` と `change_set_entries` の両 row を回収します。applied change set は commit provenance
として恒久保持します。回収時に event は発行せず tombstone も残さないため、終了状態を観測したい client は
期間内に list を polling してください。回収すると idempotency key が解放され、後で同じ key を POST すると
古いものを replay せず新しい change set を発行します。この 30 日は 7 日の idempotency TTL と 14 日の
change-set TTL より長く設定されています。sweep は stash の soft-deletion で絞り込まないため、
soft-deleted stash の change set も予定どおり回収されます。

返された cursor はすべて不透明で GC 種別に結び付いているものとして扱い、バイト単位で変更せずに
渡し直してください。null の cursor で、その pass は完了です。`maxObjects` がそれより大きくても、
R2 の各ページは 24 オブジェクトが上限ですが、入力には最大 500 を指定できます。成功レスポンスにも
ページ単位の `error` が記録される場合があるため、続行する前に確認してください。

`gc-busy` は、その種別を現在の別のフェンス済み lease が所有していることを意味します。迂回しようと
せずに処理を停止し、後で再試行してください。dry-run も同じ lease を取得して実行履歴を記録しますが、
データを削除したり進捗を永続化したりすることはありません。実行結果にもログにも、非公開 R2 のキーや
generation は含まれません。
