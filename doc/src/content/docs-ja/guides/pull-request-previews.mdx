アプリケーションの Pull Request プレビューは、対象となる一つの Pull Request 用に、使い捨ての Stash/Viewer
デプロイを準備します。これは、Cloudflare のバージョン Preview URL とも、Docs ワークフローが管理する
Docs プレビューのエイリアスおよびコメントとも異なります。

## 対象条件と分離

デプロイワークフローは、`main` または `base/**` を対象とする同一リポジトリ内の Pull Request について、
`opened`、`synchronize`、`reopened` のいずれかが発生したときに処理します。シークレットを扱う処理より前に
フォーク境界を評価します。フォークと、必要な Cloudflare 設定がないリポジトリは、意図的に成功扱いで
スキップします。`pull_request_target` を使う経路はありません。対象となる処理は、Git 認証情報の永続化を
無効にして、正確な Pull Request ヘッド SHA をチェックアウトします。

Pull Request `N` では、分離するリソース名は次のとおりです。

| リソース | 名前 |
| --- | --- |
| Stash Worker | `zudo-history-stash-pr-N` |
| Viewer Worker | `zudo-history-stash-viewer-pr-N` |
| D1 データベース | `zudo-history-stash-pr-N` |
| 非公開 R2 バケット | `zudo-history-stash-blobs-pr-N` |
| Durable Object | `StashEvents` 名前空間。その Pull Request の Stash Worker が所有します。 |

生成される非公開設定では、コミット済みのプレビュー環境をトップレベルの設定へ平坦化します。
`workers_dev` を有効にし、本番ルートとバージョンプレビューの設定を削除し、アプリケーションの cron を空に
したうえで、正確な D1、R2、サービス、オリジン、レート制限、Worker の名前を注入します。
ワークフローはこれらのファイルを `-c` でデプロイし、生成した設定に `--env preview` は適用しません。

## 証跡の順序と認証情報の境界

デプロイジョブは、次の順序で一連の処理を実行します。

1. D1/R2 リソースを確保し、二つの Worker URL を解決します。
2. 平坦化した非公開設定を生成します。
3. D1 マイグレーションを適用します。
4. 管理者認証情報を生成してマスクし、非公開のシークレットファイルを使って Stash を初回デプロイします。
5. Viewer をデプロイし、正常になるまで待ちます。
6. Viewer プロキシ経由で、決定論的な使い捨ての `demo` stash をシードします。
7. stash スコープの読み取りトークンを発行してマスクします。
8. プレビュー層の読み取り契約、厳格な Viewer HTTP スモークテスト、正確に一つの `chromium-preview`/`@preview`
   ブラウザーテストを実行します。
9. デプロイしたチェックアウトが期待する正確な SHA であることを証明し、一つのマーカーコメントを作成または
   更新します。

プレビュー契約は、保護されたファイルから管理者認証情報を受け取り、`TEST_TIER=preview` によって永続化を伴う
ケースを制限します。ブラウザーとマーカーコメントが受け取るのは、使い捨ての読み取りトークンだけです。
この意図的に公開されるトークンも Bearer 認証情報です。プレビューの外へコピーしないでください。管理者
トークン、Cloudflare API トークン、アカウント ID、非公開設定、シークレット入力を、ワークフロー出力、
コメント、成果物に含めてはなりません。障害時の成果物に含めるのは、指定された非シークレットの
デプロイログだけです。

ブラウザーでの証明には、実際の HTTPS Viewer、実際の API と SSE のトラフィックを使います。リクエストを
モックせず、コンソールを厳格に検査し、書き込み操作は提供しません。これは接続構成の証跡であり、ローカルの
ユニット、契約、ライブテストに代わるものではありません。

## 破棄と孤立リソースの回収

デプロイとクローズのワークフローは、同じ `preview-N` 並行実行キーで直列化します。手動の破棄処理は
Pull Request 番号を受け取りますが、信頼済みのベースブランチまたはデフォルトブランチのヘルパーを
チェックアウトし、変更を行う前にその正確な Pull Request がクローズ済みであることを検証します。
ロック取得後にも再検査します。

削除と不在の検証は、次の順序で実行します。

1. Viewer Worker。
2. Stash Worker と、それが所有する Durable Object 名前空間。
3. 非公開 R2 バケットを空にして確認し、削除します。
4. D1 データベースを削除して確認します。
5. 一つのマーカーコメントを、URL とトークンを含まない破棄済み状態に置き換えます。

構造化されたリソース検出で不在が証明されて初めて、クリーンアップは成功です。都合のよい CLI の一文や、
あらゆる `404` を一律に解釈した結果だけでは不十分です。定期または手動の回収処理は、ページ分割された
Worker、D1、R2 のすべてのインベントリページを和集合にし、正確なプレビュー名だけを抽出し、同じ Pull Request
ごとのフェンスの下で候補を一つずつ直列処理します。Pull Request の状態を再検査し、open 状態の Pull Request を
残し、コメントは決して編集しません。

open 状態の各プレビューは、それぞれ固有の Workers、データベース、バケット、Durable Object 名前空間、操作、
さらにアクティブなストリームを消費する可能性があります。クリーンアップにより孤立リソースの存続期間は
短くなりますが、即時ではなく、費用ゼロも保証しません。多くのプレビューを有効にする前に、現在の
アカウントクォータを監視してください。
