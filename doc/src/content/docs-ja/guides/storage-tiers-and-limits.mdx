公開モデルは、バージョン管理された正しい形式の UTF-8 テキストと、バイト列を変更しないバイナリを
サポートします。R2 への直接アクセスや汎用ファイルシステムではありません。互換性のための JSON API は
固定の `MAX_BODY_BYTES=5000000` UTF-8 byte schema 上限を持つテキスト専用経路です。デフォルトの
`JSON_INLINE_MAX_BYTES` も同じ値で、inline text access の境界を決めます。raw upload はどちらの
representation も運べます。正しい UTF-8 本文は 5,000,000 バイトを超えても `text` のままであり、サイズから
representation を推測しません。

次の判断は独立しています。

| Dimension | Values | Meaning |
| --- | --- | --- |
| Representation | `text`, `binary` | UTF-8 としてデコード・検証するか、バイト列をそのまま保持するか。 |
| Content access | `inline`, `raw`, `deleted` | レスポンスに本文を含めるか、raw でストリームするか、tombstone か。 |
| Transfer | `json`, `single`, `multipart` | 書き込みを Worker へ届ける方法。 |
| Storage | `d1`, `r2` | 物理配置。デフォルトでは `D1_INLINE_MAX_BYTES=524288` 以下を D1 に inline できます。 |
| Diff eligibility | eligible または `oversized` | 各 side が `DIFF_MAX_BYTES=524288` 以下か。ストレージとは別の契約です。 |

大きな本文は非公開のコンテンツアドレス方式 R2 オブジェクトを使い、head、履歴、ハッシュ、サイズ、
オブジェクトポインターの正本は D1 に保持します。バイナリは D1 に inline でき、大きな UTF-8 テキストは
`text` のまま R2 に保存できます。読み取り時には R2 オブジェクトの raw バイト長と SHA-256 ハッシュを
デコード前に検証します。非公開オブジェクトのキーと generation は API レスポンスやログに現れません。

raw のデフォルトは `HTTP_REQUEST_MAX_BYTES=100000000`、`SINGLE_UPLOAD_MAX_BYTES=33554432`、
`MAX_FILE_BYTES=100000000`、`MULTIPART_PART_BYTES=8388608`、stash あたり 8 セッション、
予約バイト 500,000,000、セッション TTL 86400 秒です。`MAX_FILE_BYTES` は 1,073,741,824 バイト（1 GiB）
まで設定できますが、予約容量を同じだけ確保し、part 数を 10,000 以下に保つ必要があります。これは正しさのための
上限であり、性能認証ではありません。本番 multipart part は少なくとも 5 MiB です。すべての不変条件は
[正確な上限](../reference/limits.mdx)を参照してください。

保存済み diff は、どちらか一方が diff 上限を超えると unified text の代わりに `oversized` を返します。
コンシューマーのインターフェースは、いずれかのストレージ階層ではなく、この公開結果に対応させてください。

## 名前、パス、ページ

stash 名は、小文字の ASCII 英字、数字、ハイフンからなる 1〜63 文字です。先頭は英字または数字で、
アンダースコアや大文字を含められません。ファイルパスは最大 512 UTF-8 バイトです。スラッシュで
区切られた各セグメントは、英字、数字、ドット、アンダースコア、ハイフンに一致する必要があり、
空文字、`.`、`..` は使用できません。

アプリケーションの入力を構築する前に、export された validator を使用してください。

{/* zhs-example: consumer-path-validation */}

```ts
import { validatePath, validateStashName } from "@takazudo/zudo-history-stash";

export function validateFileTarget(stash: string, path: string) {
  const stashResult = validateStashName(stash);
  if (!stashResult.ok) {
    return { ok: false as const, field: "stash" as const, error: stashResult };
  }

  const pathResult = validatePath(path);
  if (!pathResult.ok) {
    return { ok: false as const, field: "path" as const, error: pathResult };
  }

  return { ok: true as const, stash, path };
}
```

公開 wildcard 書き込みテンプレートは `PUT /v1/stashes/{stash}/files/{path}` です。ここで `{path}` は
スラッシュで区切られた残りのセグメントをすべて取り込みます。`docs/guide.md` のような実際のパスは、
そのスラッシュを維持し、`%2F` としてエンコードしてはいけません。OpenAPI 3.1 では複数セグメントの
wildcard を完全には表現できないため、生成したクライアントがこの動作を維持していることを確認して
ください。

一覧操作はデフォルトで 50 件を返し、最大 200 件まで指定できます。200 より大きな値は検証エラーであり、
ページを上限に丸めるリクエストではありません。返された cursor が null になるまで、各 cursor を
たどってください。参照されなくなった大きな本文を意図的にクリーンアップする方法については、
[stash のライフサイクルと GC](./stash-lifecycle-and-gc.mdx)を参照してください。
