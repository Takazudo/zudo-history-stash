利用側は HTTP/fetch または Cloudflare RPC binding を通じて Stash を呼び出します。通常は
[Client パッケージ](./client-package.mdx)を使用します。Viewer も、プロキシまたは binding を通じて
同じ API を使用します。D1 はメタデータと変更可能な head を保持し、大きな不変テキストは非公開の
R2 バケットへ退避できます。

## データの関係

| データ | 役割 |
| --- | --- |
| `stashes` | 一つの名前空間のライフサイクルと説明用メタデータ。 |
| `tokens` | 認証情報のハッシュ、スコープ、有効期限、失効、ローテーションのメタデータ。シークレットは復元できません。 |
| `blobs` | コンテンツアドレス方式のテキストメタデータと、インラインまたは R2 のストレージ参照。 |
| `files` | stash とパスの各組み合わせに対する変更可能な head。 |
| `versions` | 追記専用の履歴。データベース全体で一意な ID は変更カーソルでもあります。 |
| `idempotency` | 安全に書き込みを再実行するためのリクエスト同一性台帳。 |
| `gc_jobs`, `gc_runs` | 世代でフェンスされたガベージコレクションのリース、進捗、結果。 |
| `proposals` | フェンスされた判断状態を持つ不変の候補。 |

## 書き込みプロトコル

1. 認可、パス、リクエスト上限、期待する head を検証します。
2. 大きい可能性がある不変オブジェクトを、データベーストランザクションより先に R2 へ保存します。
3. フェンスされた一つの D1 バッチで blob を記録または再利用し、version を追加して、最後にファイル
   head の変更を公開します。
4. 冪等性の結果を記録し、助言的なライブアクティビティを公開します。

compare-and-set のフェンスにより、更新の消失を防ぎます。R2 へのアップロード後にフェンスで負けた場合、
そのオブジェクトはガベージコレクションまで未参照のまま残ることがありますが、ファイルの head には
なりません。作成、更新、削除、ロールバック、インポート、提案の承認はすべてフェンスを使用します。
ロールバックは新しい version を追加するものであり、履歴を過去へ戻すものではありません。また、提案の
承認には、リベースではなく提案の正確なベース head が必要です。

冪等性キーは一つの正規リクエストを識別します。内容を変えてキーを再利用すると
`422 idempotency-key-reused` エラーになり、再実行した操作を変更する許可にはなりません。

## ライフサイクルと復旧

stash の削除は論理削除であり、処理は延期されます。削除により有効な stash 認証情報は失効します。
復元するとデータは保持されますが、それらの認証情報は復活しません。ガベージコレクションは世代で
フェンスされたリースを使用するため、期限切れの実行者が後継の作業を完了または解放することはできません。
上限付きの各実行はすべて記録されます。

ライブ配信は replay より先に購読し、その後で助言的なイベントを発行します。利用側は `ready`、
`change`、`proposal`、再接続の後に、正本である変更フィードとリソース読み取りを使って照合する必要が
あります。イベントストリームは第二の正本ではありません。
