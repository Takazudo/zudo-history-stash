各ブランチと Pull Request は、一つの契約または実装領域に集中させてください。機能ブランチは意図した
統合ブランチを基点とし、共有履歴を維持して、実行した正確なコマンドと収集した証跡を記録します。
実行しなかった重要なブラウザー、ライブ、インフラストラクチャ、デプロイの検査も列挙してください。

## 公開契約全体を変更する

公開ルート、スキーマ、エラー、パッケージ API、Viewer URL、バインディング、運用コマンドを変更するときは、
実装、対象を絞ったテスト、正本となるドキュメント、生成済みの OpenAPI/リファレンス成果物も一緒に更新します。
検査対象の出力は手で編集せず、そのソースから再生成してください。フェイクだけを使ったテストは決定論的な
動作を証明できますが、HTTP、Worker、ブラウザー、ストレージ、プラットフォームの証跡には代わりません。

Cloudflare の認証情報、Worker シークレット、Bearer トークン、`.dev.vars`、生成した非公開のプレビュー設定、
ローカルストレージの状態をコミットしてはなりません。破壊的なテストは分離されたローカルリソースで行い、
プレビューでの変更はレビュー済みの使い捨てワークフローに限定します。本番環境の受け入れ確認は読み取り専用の
ままにしてください。

開発中は対象パッケージのテスト、型検査、ビルドを実行します。引き渡しの前に、依存関係を扱う段階で
実行できる場合は、ルートの `pnpm b4push` を実行してください。Docs の変更では、単一の集約コマンド
`pnpm b4push:doc` も実行します。ブラウザー、ライブ、インフラストラクチャの各レーンでは、URL、認証情報、
変更操作のガードを維持し、必要な場合は個別に記録してください。

## リリースを準備して公開する

プレリリースやビルド接尾辞のない SemVer 形式のリリースと必要なリリースノートを準備するには、リポジトリの
`/l-make-release` コマンドを使います。正確な `vX.Y.Z` タグを作成する前に、すべてのパッケージバージョン、
エクスポートされるバージョン定数、生成した OpenAPI バージョン、そのほかの検査対象となるリリース成果物を
同期しなければなりません。

リリースワークフローは、npm の `latest` dist-tag で Core、Client、UI の順に公開し、依存する各バージョンが
確認できるまで待ちます。手動の `workflow_dispatch` では処理列全体をドライランモードで実行し、公開は
決して行いません。ワークフローを任意のローカル公開コマンドに置き換えないでください。

タグ付きの実行で一つのパッケージを公開した後に一時的な障害が発生した場合は、同じ変更不可能なタグを
再実行します。ワークフローは、すでに存在する正確なバージョンを安全にスキップし、依存順に処理を続けます。
公開済みの npm バージョンは変更できません。コードまたはワークフローのロジックを変更する必要がある場合は、
古いバージョンを上書きまたは修復せず、メインライン上で前方修正して新しいパッチリリースを作成してください。

リリースノートはコントリビューターとしての契約の一部であり、ユーザーから見える動作、マイグレーション、互換性、
運用上必要な対応を記述しなければなりません。特定のファイルパスを恒久的なポリシーとして扱わず、ノートの
作成場所について現在のリリースツールに従ってください。
